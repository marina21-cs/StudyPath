## Proposed experience

Planner should start with four always-visible destinations: **Grades & Scores**, **GWA**, **What-if**, **Prerequisite Map**, followed by semester subjects and upcoming work. Missing setup opens an actionable setup state; it does not hide the destination or fabricate a result. A subject card also has a Grades action. Selecting any course from these destinations must use the same explicitly mapped subject/course identity.

Grade setup records syllabus/template, category weights and aggregation, assessments, scale/conversion, units, excluded/missing work, retakes and rounding. Template states are Draft, Awaiting review, Approved and Outdated. A student checkbox cannot establish professor approval. For the first pilot, the professor reviews the actual syllabus/template outside the app; a maintainer publishes the verified version/provenance through existing trusted catalog tooling. Display that evidence in the app. Direct in-app professor accounts, approval authorization and audit trails are a separate proposed extension; the current specification excludes a teacher portal. Policy-dependent results remain unavailable until applicable review exists. A new personal-calculator mode would require a deliberate contract change, not removal of existing guards.

COR course names are not enough to infer units, grading rules or prerequisites. Explicitly map each personal subject to the correct reviewed course/term; retain unlinked personal material. Keep recorded assessment scores, manually entered final grades, practice results and hypothetical scenarios separate. Reuse existing formula engines instead of implementing competing arithmetic in screen code.

A prerequisite graph should show course nodes, edges, AND/OR groups, direction, completed/in-progress/unmet/unknown labels and a tap-to-inspect explanation. Provide zoom/recenter and a full accessible list. Personal links can be displayed immediately as an unreviewed planning map, without inferred pass/eligibility; reviewed evaluation uses exact applicable rules. Missing prerequisites and cycles must be explicit.

Materials should offer **Paste PDF link**, **Import from device** and **Create study card**. The pasted-link flow is link → preview source/title and choose subject → download progress/cancel/retry → validated Ready offline. Receive shared URLs and PDF content URIs through a dedicated validated intake. A copied local filename/path is not necessarily a usable URL; file apps should use Share. Login pages and cloud-preview URLs may need browser download/import fallback. Use existing PDF signature/render validation, per-file/aggregate bounds, app-private atomic storage and duplicate handling; only mark offline after verified completion. Preserve original source metadata, reading place and material identity. A failed/cancelled import must not create a phantom ready item. PDF organization, offline retention and study-card linkage remain useful even for an already downloaded file.

## Wikipedia research decision

Keep the official MediaWiki REST HTML/revision/license contract and existing jsoup native stack. Extract only article content with a deterministic, tested block walker. Mozilla Readability is a useful reference/benchmark, but embedding a JavaScript engine or introducing a server solely for this Wikipedia bug adds unnecessary scope. TextExtracts has documented citation/newline/formula limitations and is not a guaranteed clean replacement. Preserve attribution, paragraph/list structure and an explicit fallback for unsupported table/math content. Version the extractor and offer refreshed copies of affected saved readings; never silently overwrite notes or reinterpret character offsets against different text.

Sources inspected: [MediaWiki REST reference](https://www.mediawiki.org/wiki/API:REST_API/Reference#Get_page_with_HTML), [MediaWiki DOM](https://www.mediawiki.org/wiki/Specs/HTML), [jsoup](https://jsoup.org/), [Mozilla Readability](https://github.com/mozilla/readability), [TextExtracts caveats](https://www.mediawiki.org/wiki/Extension:TextExtracts#Caveats), [Android receiving shared data](https://developer.android.com/training/sharing/receive), [Android transfer choices](https://developer.android.com/develop/background-work/background-tasks/data-transfer-options). Android intent/background-transfer concepts apply without migrating Kotlin/XML UI to Compose.

## Delivery and acceptance

The [eight-step implementation plan](../../feedback-recovery-plan.md) puts visibility, reading cleanup and PDF-link intake first; then explicit subject mapping, reviewed templates, surfaced calculators and the graph. Each shipped batch ends in focused tests and actual light-device checks. Important checks include empty catalog discoverability, wrong/revoked policy, preserved 0.1.6 data, zero vs ungraded, GWA attempt inclusion/retakes, stale hypothetical scenarios, graph AND/OR unknown states, interrupted PDF downloads and offline reopen. Real syllabus/scale/prerequisite evidence remains a dependency for academic acceptance.
